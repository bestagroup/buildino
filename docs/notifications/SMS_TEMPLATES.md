# استاندارد پیامک قالب‌محور بیلدینو

## قرارداد فعال

همه پیامک‌های قاصدک از endpoint فعلی Verify و با `type=1` ارسال می‌شوند. نام قالب حساس به مقدار دقیق تنظیم‌شده است.

| کاربرد | کلید داخلی | template پیش‌فرض | param1 | param2 | param3 |
|---|---|---|---|---|---|
| ورود و تأیید شماره | auth.otp | buildinoverify | کد یک‌بارمصرف | ارسال نمی‌شود | ارسال نمی‌شود |
| دعوت عضویت واحد | unit.invitation | BuildinoInvitation | کد دعوت | نام و نام خانوادگی مخاطب | نام ساختمان، واحد شماره … |

`receptor` در هر دو مسیر شماره موبایل مخاطب است. کدها رشته هستند؛ صفر ابتدای کد حفظ می‌شود. متن فارسی یا اعداد موجود در نام ساختمان به هیچ عنوان برای استخراج کد پردازش نمی‌شوند.

نام دعوت‌شونده از کاربر مرتبط و در دعوت‌های قدیمی از تطبیق شماره موبایل خوانده می‌شود. اگر نام ثبت نشده باشد، «کاربر گرامی» ارسال می‌شود. نام ساختمان و شماره واحد از زنجیره واحد ← طبقه ← بلوک ← ساختمان گرفته می‌شود؛ ورودی آزاد درخواست برای این اطلاعات استفاده نمی‌شود. ارسال مجدد همان قالب را با کد جدید و اطلاعات تازه پایگاه داده استفاده می‌کند.

## تنظیم سرور

```dotenv
SMS_PROVIDER=ghasedak
GHASEDAK_API_KEY=YOUR_EXISTING_PRIVATE_KEY
GHASEDAK_ENDPOINT=https://api.ghasedaksms.com/v2/send/verify
GHASEDAK_TYPE=1
SMS_TEMPLATE_AUTH_OTP=buildinoverify
SMS_TEMPLATE_UNIT_INVITATION=BuildinoInvitation
```

کلید واقعی موجود را نگه دارید؛ مقدار نمونه بالا را جایگزین آن نکنید. هر دو قالب باید در پنل قاصدک با همین نام و ترتیب پارامتر تأیید شده باشند. متغیر قدیمی `GHASEDAK_TEMPLATE` دیگر استفاده نمی‌شود. مقادیر پیش‌فرض دو قالب در `config/notifications.php` وجود دارند.

پس از استقرار کد و تنظیم محیط:

```sh
php artisan config:cache
php artisan queue:restart
```

Migration و Build فرانت‌اند لازم نیست. صف‌های فعال باید توسط worker یا سازوکار موجود هاست دوباره اجرا شوند.

## افزودن بخش بعدی

1. ابتدا گیرنده، رویداد ارسال، نام قالب تأییدشده و ترتیب پارامترها مشخص شود.
2. در `notifications.sms_templates`، تعریف تو‌در‌تو برای purpose اضافه شود. مثال زیر صرفاً راهنمای توسعه است و در تنظیم فعال وجود ندارد:

```php
'invoice' => [
    'issued' => [
        'template' => env('SMS_TEMPLATE_INVOICE_ISSUED'),
        'parameters' => ['param1', 'param2'],
    ],
],
```

3. برای ارسال مستقیم، `SmsTemplateMessage` ساخته شود:

```php
$message = new SmsTemplateMessage('invoice.issued', [
    'param1' => $invoice->invoice_number,
    'param2' => (string) $invoice->outstanding_amount,
]);
$sms->send($recipient->mobile, $message);
```

4. در اعلان‌های صفی موجود، از نوع همان اعلان و `data['sms_parameters']` برای نگاشت صریح استفاده شود. مسیر `UserNotificationService` همان registry را مصرف می‌کند و کنترل ترجیحات کاربر، وضعیت حساب و جلوگیری از ارسال تکراری را حفظ می‌کند. قالب قاصدک از متن اعلان استخراج نمی‌شود.
5. برای هر بخش تست درخواست خروجی، مجوز/محدوده گیرنده، پارامتر ناقص، خطای درگاه و ارسال مجدد مرتبط اضافه شود. کد یا پارامتر حساس در متن اعلان عمومی یا لاگ نوشته نشود.

## رفتار خطا و سازگاری

- Registry باید دقیقاً مجموعه پارامترهای تعریف‌شده را دریافت کند. پارامتر خالی، اضافی، نام ناشناخته یا مقدار غیررشته‌ای پذیرفته نمی‌شود.
- ارسال مستقیم متن خام با قاصدک ممنوع است؛ قالب ورود هرگز fallback بخش‌های دیگر نیست.
- اعلان‌های پیامکی عمومی فاقد قالب در حالت `ghasedak` ارسال نمی‌شوند و لاگ موفق جعلی برای آن‌ها ساخته نمی‌شود. سایر کانال‌ها مستقل باقی می‌مانند. برای فعال شدن این پیامک‌ها، تنظیم قالب و نگاشت داده هر دو لازم است؛ اعلان‌های قدیمی خودکار دوباره ارسال نمی‌شوند.
- رابط `SmsSender` برای سازگاری درایورهای قدیمی HTTP/Log هنوز متن خام را می‌پذیرد. پیام‌های قالبی در درایور HTTP با `template` و پارامترهای صریح ارسال می‌شوند؛ قرارداد قبلی متن خام آن تغییر نکرده است. این درایور عمومی جایگزین خودکار قاصدک نیست.
- علاوه بر وضعیت HTTP، در پاسخ تخت مقدار صریح `result="success"` بررسی می‌شود؛ در پاسخ تو‌در‌تو، `result.code=200` معیار است. وضعیت عددی خطا در پاسخ تخت حتی کنار success پذیرفته نمی‌شود. خطا یا پاسخ نامعتبر، ارسال موفق محسوب نمی‌شود. پذیرفته شدن توسط درگاه به معنای تحویل قطعی به گوشی نیست.
- درایور Log کد ورود، کد دعوت یا پارامترهای شخصی را ثبت نمی‌کند. افزودن retry خودکار به درخواست HTTP انجام نشده تا احتمال ارسال تکراری در timeout افزایش نیابد.

## اعتبارسنجی این تغییر

- مجموعه منتخب ورود، ثبت‌نام، دعوت، قرارداد قالب و اعلان عمومی: ۵۸ تست و ۵۸۶ assertion موفق.
- تست تکمیلی ارسال و ارسال مجدد دعوت با درایور قاصدک و HTTP جعلی: ۱ تست و ۵ assertion موفق.
- وابستگی‌های اعلان (کنترل ارسال هم‌زمان، حذف توکن نامعتبر و حذف اطلاعات حساس): ۹ تست و ۴۰ assertion موفق.
- کل پروژه مجدداً تست نشده است. ارسال واقعی پیامک، تأیید قالب در پنل قاصدک و استقرار روی سرور انجام نشده‌اند.

## عیب‌یابی پاسخ درگاه

اگر ارسال ناموفق باشد، پیام خطا اکنون HTTP، کد `result.code`، نوع خطا و نام فیلدهای شناخته‌شده اشاره‌شده در پاسخ را نمایش می‌دهد. نمونه صرفاً آموزشی:

```text
Ghasedak SMS failed [HTTP=200; code=400; reason=provider_rejection; fields=template].
```

- `provider_rejection`: در پاسخ تخت result خطاست یا کد پاسخ قاصدک موفق نیست؛ فیلدهای ذکرشده سرنخ بررسی هستند، نه تشخیص قطعی.
- `non_json_response`: پاسخ JSON معتبر با ساختار شیء/آرایه دریافت نشده است؛ endpoint یا واسطه شبکه بررسی شود.
- `unexpected_response_schema`: پاسخ با هیچ‌یک از ساختارهای صریح پشتیبانی‌شده تطابق ندارد. بدون مشاهده قرارداد واقعی، چنین پاسخی موفق تلقی نمی‌شود.

این اطلاعات با پیام `Ghasedak SMS request failed` نیز در لاگ برنامه ثبت می‌شوند؛ بدنه خام پاسخ، کلید API، شماره موبایل و کد ورود ثبت نمی‌شوند. برای عیب‌یابی همین خطای خلاصه را ارائه کنید. صرف وجود HTTP 200 یا پارامتر `status=200` در ساختار ناشناخته کافی نیست.

اعتبارسنجی اصلاح تشخیص خطا: ۲۰ تست مرتبط و ۵۶ assertion موفق؛ سناریوهای خطای قالب، رد HTTP، پاسخ HTML، ساختار ناشناخته، کد نامعتبر و عدم افشای اطلاعات حساس پوشش داده شدند. علت خطای واقعی سرور تا دریافت تشخیص جدید مشخص نیست.


## اصلاح سازگاری با پاسخ api.ghasedaksms.com

در بررسی مستقیم بدون API Key و بدون receptor، درخواست POST خالی به endpoint فعلی این پاسخ را برگرداند:

```json
{"result":"error","message":"invalid parameter"}
```

این بررسی هیچ پیامکی ارسال نکرد. بنابراین فرض اجباری بودن `result.code` برای این درگاه نادرست بود. اکنون پاسخ تخت با `result="success"` و شناسه `messageids[0]` پشتیبانی می‌شود؛ اگر status/code عددی وجود داشته باشد باید 200 باشد. result خطا، وضعیت متناقض، داده نامعتبر و HTTP ناموفق پذیرفته نمی‌شوند. قرارداد تو‌در‌توی قبلی و مسیرهای شناسه آن نیز حفظ شده‌اند. جزئیات امن خطا شامل format و result شناخته‌شده است و متن یا مقادیر حساس درگاه چاپ نمی‌شوند.

اعتبارسنجی این اصلاح: ۲۸ تست قرارداد/درگاه با ۷۸ assertion؛ سپس ۲ تست هدفمند ورود و دعوت/ارسال مجدد با پاسخ تخت و ۷ assertion موفق. پاسخ موفق حساب واقعی و تحویل پیامک هنوز از محیط سرور کاربر تأیید نشده است.
